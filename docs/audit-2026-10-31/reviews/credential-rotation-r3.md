## R2-F1: independently verified disposition

The following references are to `scripts/rotate-postgres-credentials.py` in `/thinisde/trady`.

- **Independent lock-session settings and identity:** `AdministrativeSession.__init__`, lines 248–262, starts one persistent `docker exec -i ... psql` process with stdin/stdout pipes, discarded stderr, `env -i`, a fixed PATH, `PGOPTIONS=-c idle_session_timeout=0`, `-X`, `-w` and `ON_ERROR_STOP=1`. It explicitly selects `/var/run/postgresql:5432`, database/user `postgres`. Saved DSN options are not passed into this administrative connection. `database_lock`, lines 309–319, first verifies the saved analyst endpoint, then acquires `pg_try_advisory_lock(8153212011::bigint)` and obtains the backend PID through this same session. A rejected lock never reaches the protected rotation body.
- **Operations remain with the lock holder:** `_rotate_database_locked` binds its local `admin` to `session.admin` at line 381. Restricted-role checks, HBA inspection, password-encryption/verifier reads, all nine password prompts, the precommit liveness query, reload, termination and every verifier-restoration attempt use that binding, at lines 384–452. The only top-level administrative calls reached by the rotation flow are the initial `show port` at line 368 and the read-only live-session identity probes in `same_server`, lines 227–237. There is no protected mutation or restoration fallback through the top-level helper.
- **Failure stops later commands on that session:** `AdministrativeSession.admin`, lines 264–294, rejects a different container, a failed session or an exited process before writing. It frames each command with a fresh random completion marker, waits using a thirty-second deadline, enforces a 256 KiB pending-output limit, and treats EOF, timeout, decoding and pipe/read errors as failure. Its exception path sets `failed=True` and emits a generic suppressed-detail error. It creates no replacement process or connection. A subsequently attempted restoration therefore cannot reconnect and overwrite another rotation's verifiers after the coordinator connection is lost.
- **Password and verifier argument semantics:** The process argument vector is constructed once from the container and fixed configuration, before any password or verifier is supplied. `AdministrativeSession.admin` writes SQL and prompt input exclusively to the process's stdin. SQL receives a statement separator; the fixed `\password ROLE` commands receive a newline followed by the two password-input lines and then the completion query. All role names come from `ROLES`; newly generated passwords use `secrets.token_urlsafe(48)`. `private_sql=True` needs no alternate transport in this session because every command already uses stdin. Neither plaintext passwords nor restoration verifiers are appended to subprocess arguments.
- **Restoration and cleanup:** `_rotate_database_locked`, lines 445–460, attempts all nine saved-verifier restorations before replacement and records restoration failures instead of stopping at the first role. An injected higher-level failure can restore through a still-healthy lock-owning session. An unusable session rejects those attempts and produces the documented incomplete-restoration error; it never starts a separate administrator. The staged file is unlinked in `finally`. `database_lock` closes the session in `finally`; `AdministrativeSession.close`, lines 296–305, closes its selector and stdin, waits up to five seconds, kills the local process after a wait timeout, waits again, and closes stdout. `rotation_lock` releases its descriptor in its own `finally`.
- **Commit ordering and failure boundary:** Lines 425–436 query the same session immediately before the final credential text/inode recheck and atomic replacement. `committed=True` follows `os.replace` immediately and precedes parent-directory open/fsync. Consequently directory-fsync, reload, postcommit authentication or termination failures do not restore old verifiers against the replaced store. The liveness query is a check before replacement; it does not make filesystem replacement atomic with a database connection's lifetime. The source and contracts also retain the explicit best-effort qualification for editors that ignore the locks.

The round-2 counterexample depended on an expiring analyst lock connection plus independent administrative mutation/restoration. The current lock connection does not inherit the analyst DSN's timeout, explicitly overrides the administrator's idle-session timeout at startup, and owns the protected commands. The independent stale-restoration path is removed.
