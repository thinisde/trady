# Trading bot design plan

> Historical design input. The current [Trady v1 specification](./README.md)
> incorporates the newer requirements and supersedes this document where they
> differ, including language, database, allocation, source coverage, Telegram,
> and same-day exits. The original design text is retained below for reference.

I would build this as a **small, auditable trading system with an LLM analyst—not an LLM with unrestricted access to your brokerage account.**

The separation is:

**News and market data → LLM recommendation → rules enforced by code → broker order → performance records.**

Your €50 should be treated as an experimental trading balance, not as evidence that the strategy will be profitable. The first goal is to prove that the bot follows its rules, handles failures correctly, and reports its actual results.

## 1. Define the trading rules precisely

These would be the initial operating rules. The €45 entry budget and €5 cash reserve are my proposed defaults; the €50 capital, one-stock limit, and daily trading limit come from your requirements.

| Setting | Initial design |
|---|---|
| Starting trading capital | **€50 total**, with no automatic deposits |
| Account type | Cash-only investing account |
| Instruments | Ordinary stocks; fractional shares where supported |
| Maximum holdings | **One stock at a time** |
| Daily trading limit | **At most one buy or sell order per market session** |
| Entry budget | Up to €45, including estimated entry costs |
| Cash reserve | Preserve at least €5 when opening a position |
| Borrowing, leverage and short selling | Disabled |
| Adding to an existing position | Disabled in version 1 |
| Holding overnight | Allowed |
| Doing nothing | Always allowed |
| Initial operating mode | Paper trading |

### What “one trade per day” means

A purchase is one trade. A sale is another trade.

Consequently, the bot may buy on Monday and sell on Tuesday, but **cannot buy and sell on Monday**. It also cannot sell one stock and buy another on the same day.

Partial executions of the same broker order count as one logical order. For additional protection, the first version should permit only **one order-submission attempt per session**, even if that order is rejected or cancelled.

**Important consequence:** under your strict rule, a stock bought in the morning cannot be automatically sold that afternoon—even when bad news appears. A same-day emergency exit would require you to explicitly change the rule. This design does not silently add that exception.

This makes the bot a **low-frequency, overnight-holding strategy**, rather than an intraday buy-and-sell system.

## 2. Overall architecture

Use one application repository with clearly separated modules. There is no need for a complex collection of cloud services.

| Component | Responsibility |
|---|---|
| **Scheduler** | Runs pre-market analysis, midday analysis, reconciliation and weekly review |
| **X news collector** | Fetches a small, targeted set of recent posts |
| **Evidence verifier** | Deduplicates stories and checks material claims against original sources |
| **Market-data adapter** | Supplies prices, bid/ask quotes, market status and historical prices |
| **Knowledge retriever** | Retrieves approved rules and relevant historical decisions |
| **LLM adapter** | Sends structured context through an OpenAI-style API and receives a recommendation |
| **Risk and policy engine** | Enforces cash, position, daily-order and data-quality restrictions |
| **Execution service** | Places approved orders and reconciles their actual status |
| **Database and reporting** | Records decisions, orders, executions, portfolio value and operating costs |

Only the **execution service** receives a broker credential with trading permission. The LLM receives neither that credential nor a direct `place_order` tool.

For deployment, I would use **Python on your Ubuntu server, SQLite for the initial database, and a service manager that restarts the application after failures**. Keep the executor isolated from the analysis process, even if both run on the same machine.

## 3. Broker and market-data connections

### Broker: Trading 212 as the initial candidate

For this small experiment, I would prototype against **Trading 212 Invest’s demo API**, while retaining a replaceable `BrokerAdapter`.

Its current official documentation provides demo and live environments. Its help centre confirms live API support for market, limit, stop and stop-limit orders. The API remains in beta, and account-currency restrictions apply. [Trading 212](https://docs.trading212.com/api)

Trading 212 also documents fractional-share support, including fractional limit orders. Nevertheless, verify the exact instrument, quantity precision and API permissions on your account before enabling live execution. [Trading 212](https://helpcentre.trading212.com/hc/en-us/articles/9511997937437-Can-I-trade-with-fractional-shares?utm_source=chatgpt.com)

The adapter should expose a small internal interface:

```text
get_account()
get_positions()
get_open_orders()
get_order(order_id)
get_recent_executions()
get_instruments()
submit_limit_order(validated_order)
cancel_order(order_id)
```

Other parts of the application must not depend on Trading 212-specific field names.

### Market data: a separate dependency

Do not assume that a brokerage order API also supplies everything needed for price analysis. Trading 212’s published API covers account information, instruments, positions, orders and history, rather than a general historical-candle or streaming-quote service. [Trading 212](https://docs.trading212.com/api)

Create a separate `MarketDataAdapter` returning:

```text
instrument_id
bid
ask
last_price
quote_timestamp
quote_currency
feed_and_venue
market_open
trading_halted
```

For a US-stock paper prototype, **Alpaca Basic is a possible data source**, but its free real-time stock coverage is IEX-only, not the consolidated US market. Do not represent those quotes as the best prices across all exchanges. [Alpaca US](https://docs.alpaca.markets/us/docs/about-market-data-api)

**Live-trading gate:** a suitable, authorised price feed must be configured and its coverage understood. Without it, the bot remains in paper mode. Never silently substitute stale prices scraped from a website.

## 4. Scheduled behaviour

For the worked design, I will assume a small watchlist of **US-listed stocks**. The exchange calendar remains configurable.

The NYSE regular session is normally 09:30–16:00 Eastern Time, with holidays and some early closes. Scheduling must follow the exchange calendar rather than fixed German clock times. [New York Stock Exchange](https://www.nyse.com/markets/hours-calendars)

| Job | Schedule | Behaviour |
|---|---|---|
| **Pre-market analysis** | 30 minutes before the regular open | Collect news, verify evidence, review the holding and prepare a recommendation |
| **Opening execution check** | 15 minutes after the regular open | Refresh prices and account state; execute only if the morning proposal still passes all checks |
| **Midday analysis** | 12:00 exchange-local time, when the market is open | Fetch new information and reassess; may trade only if today’s slot remains unused |
| **End-of-day reconciliation** | 10 minutes after the session closes | Reconcile orders, executions, cash and portfolio value |
| **Weekly review** | 30 minutes after the final trading session of the week | Calculate results and produce a review |

For US trading, use `America/New_York` internally and display reports in `Europe/Berlin`. This avoids errors when American and European daylight-saving changes occur on different dates.

The bot should also check order status while an order is pending. That does **not** require another LLM call.

### Midday decision rules

If the bot bought this morning, midday analysis can recommend holding or flag a problem, but cannot submit another trade.

If it held a stock from a previous day and has not traded today, it may sell.

If it is in cash and has not traded today, it may buy.

If it sold this morning, it remains in cash until a later session.

Missed jobs should not trigger late “catch-up” orders based on expired recommendations.

## 5. News collection and verification

### Keep the initial universe small

Start with **five to ten manually approved, liquid stocks**, not every company mentioned on X. The watchlist should be configuration controlled, not something the LLM can expand.

Each instrument needs an unambiguous mapping between the news symbol, exchange, currency and broker instrument identifier.

### X collection

Use the recent-search endpoint with a fixed set of queries covering the watchlist, the current holding and relevant market-wide developments. X’s recent search currently covers the preceding seven days. [X Developer Platform](https://docs.x.com/x-api/posts/recent-search)

A proposed collection policy is:

```text
Pre-market:
    Fetch relevant posts since the previous successful collection.
    Include the weekend when appropriate.

Midday:
    Fetch only posts newer than the morning collection.

Each run:
    Limit results and pagination.
    Deduplicate by post ID and underlying news event.
    Record whether collection was complete or budget-limited.
```

Store `published_at`, `event_time` where known, and `first_seen_at` separately. A newly posted link to an old story is not necessarily new information.

### Evidence verification

The collector should prioritise an approved source list, but an approved account is not proof that every claim is correct.

Before a material headline can justify a new position, seek confirmation from an original source such as a company announcement, filing or official economic release. Several posts copying the same rumour are **one piece of evidence**, not several independent confirmations.

A proposed evidence record:

```json
{
  "evidence_id": "event_0042",
  "instrument_id": "watchlist_instrument_03",
  "event_type": "earnings_guidance",
  "published_at": "...",
  "first_seen_at": "...",
  "source_ids": ["..."],
  "primary_source_verified": true,
  "summary": "...",
  "contradictions": [],
  "permitted_for_llm_processing": true
}
```

### X content and LLM processing

Make permissions a launch requirement. X restricts redistribution and requires stored content to reflect deletions or changes. Its agreement also prohibits using X content to train or fine-tune foundation/frontier models. [developer.x.com](https://developer.x.com/en/developer-terms/agreement-and-policy)

Do not assume that an API subscription grants unrestricted permission to forward raw posts to any LLM provider. Confirm the applicable terms for your processing arrangement; otherwise use X for discovery and independently obtain permitted source material for analysis.

## 6. The OpenAI-style LLM interface

Build a provider-neutral adapter rather than tying strategy code to one model.

```yaml
llm:
  api_style: openai_chat_completions
  base_url: ${LLM_BASE_URL}
  api_key_env: LLM_API_KEY
  model: ${LLM_MODEL}
  timeout_seconds: 30
  max_output_tokens: 1200
  require_validated_structured_output: true
```

For OpenAI directly, support a separate Responses API implementation. OpenAI recommends Responses for new integrations; Chat Completions remains a useful interface to support when compatibility with other providers is required. [OpenAI Developers](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create?utm_source=chatgpt.com)

“OpenAI-compatible” should not be assumed to mean identical capabilities. Test the chosen provider’s schema support, error responses and token accounting.

### What the model receives

Each request contains the current account snapshot, remaining daily trading allowance, verified news, timestamped market data, approved strategy rules and a small selection of relevant past decisions.

The model proposes **`BUY`, `SELL`, `HOLD` or `NO_ACTION`**.

It does not determine the final cash balance, share quantity or whether a restriction may be bypassed.

Example output:

```json
{
  "action": "NO_ACTION",
  "instrument_id": null,
  "evidence_ids": ["event_0042"],
  "reason": "The announcement is verified, but the price has moved beyond the permitted entry range.",
  "thesis": null,
  "invalidation_conditions": [],
  "uncertainties": [
    "The available quote feed has limited venue coverage."
  ]
}
```

Use a strict schema where supported and validate the response again locally. OpenAI’s Structured Outputs supports schema-constrained responses, but your application still needs to handle refusals, incomplete responses and other failures. [OpenAI Platform](https://platform.openai.com/docs/guides/structured-outputs)

**Invalid response, missing evidence, timeout or unknown instrument → no new trade.**

Do not treat an LLM’s self-reported confidence as a measured probability of profit. The model’s explanation is a hypothesis to evaluate, not evidence that the strategy works.

### Prompt-injection protection

Treat posts, linked articles and retrieved notes as untrusted data. They must not be able to change the system instructions, request secrets, execute code or change trading limits.

The news fetcher should follow only approved destinations and never give article text authority to invoke the executor.

## 7. Risk controls and reliable execution

This is the most important engineering component.

### Checks before an order

| Check | Required behaviour |
|---|---|
| Daily order slot | Reject a second submission attempt |
| Current holdings | Reject a buy whenever a stock is already held |
| Pending orders | Reject conflicting or unresolved orders |
| Instrument | Require an exact match to the approved watchlist |
| Cash | Require sufficient verified spendable cash; never assume pending sale proceeds are usable |
| Entry budget | Include estimated fees, conversion and applicable transaction charges |
| Quote quality | Require a recent, valid quote and a permitted market session |
| Recommendation | Require a non-expired proposal with valid evidence references |
| Account consistency | Stop new orders when broker state differs from local records |
| Operating mode | Prevent paper credentials/configuration from switching to live automatically |

For version 1, use **limit orders**, not unrestricted market orders. The code calculates quantity from the validated budget and limit price, rounds down to the supported precision, and checks the total estimated cost again.

A limit order may not fill. The bot must accept that outcome rather than repeatedly chasing the price.

### Prevent duplicate orders

The application should reserve the daily trading slot in a database transaction **before** contacting the broker:

```text
Reconcile account
    → validate proposal
    → atomically reserve daily slot
    → persist order intent
    → submit once
    → record broker order ID
    → reconcile actual executions
```

Use a unique database key such as:

```text
(broker_account_id, market_session_date)
```

Trading 212 explicitly warns that its order-placement endpoints are not idempotent: repeating a request can create duplicate orders. [Trading 212](https://docs.trading212.com/api/orders?utm_source=chatgpt.com)

Therefore, when a submission times out, its state becomes **UNKNOWN**, not “failed, retry.” Check broker orders and execution history first. If the outcome cannot be established, stop and alert you.

### Pending orders and external activity

Prefer session-limited orders, cancel remaining unfilled quantities before the configured cutoff, and confirm the cancellation. Unresolved orders block subsequent trading.

Use an account reserved for this experiment. Manual trades, other bots and automatic investment features can invalidate the one-stock and daily-order guarantees.

Unexpected holdings—including those created by corporate actions—should trigger a pause and reconciliation, not an improvised sale.

### Loss handling

A proposed initial review threshold is **€5 below starting equity**. Crossing it blocks new buys and alerts you; permitted risk-reducing exits remain possible subject to the daily rule.

This is an intervention threshold, **not a guaranteed €5 maximum loss**. In particular, the strict daily limit can prevent an immediate exit after a morning purchase.

## 8. Knowledge base and database

Separate **rules**, **observations** and **financial records**.

### Knowledge base

| Category | Examples | Modification rights |
|---|---|---|
| Approved policy | Capital limits, watchlist, order rules | You only |
| Instrument information | Broker identifier, currency, precision, market calendar | Validated synchronisation |
| Research evidence | Verified events, source references, timestamps | Collector/verifier |
| Historical observations | Previous decisions and outcomes | Reporting process |
| Proposed improvements | Weekly-review suggestions | LLM may propose; you approve |

Start with tagged documents and database queries. A vector database is optional later, not a requirement for a €50 prototype.

Retrieve relevant losing trades and `NO_ACTION` decisions as well as winners. Otherwise the knowledge base risks becoming a collection of flattering examples.

The weekly review must not automatically rewrite trading policy or increase risk limits.

### Database tables

| Table | Records |
|---|---|
| `runs` | Job, scheduled time, actual time, status and errors |
| `news_items` / `evidence` | Source identifiers, timestamps, verification and retention state |
| `market_snapshots` | Quotes, currencies, venue coverage and timestamps |
| `decisions` | Model recommendation, evidence references, prompt/model versions |
| `risk_checks` | Each validation result and rejection reason |
| `daily_trade_slots` | Durable reservation of the daily allowance |
| `orders` / `fills` | Intent, broker identifiers, statuses and actual executions |
| `cash_events` | Deposits, withdrawals, dividends, fees and taxes |
| `portfolio_snapshots` | Cash, holding value and total account equity |
| `operating_costs` | X, LLM, data and hosting costs |
| `weekly_reviews` | Metrics, observations and proposed changes |

Use decimal arithmetic for money and quantities, and UTC timestamps for storage.

Keep financial events append-only, with correcting entries rather than silent edits. Keep licensed source content separately so it can be updated or deleted without destroying the trade ledger.

## 9. Weekly performance review

The reporting code calculates the numbers. The LLM explains them.

The report should cover:

| Area | Measures |
|---|---|
| Account result | Starting equity, ending equity, realised and unrealised profit/loss |
| Costs | Broker charges, FX, taxes withheld and external operating expenses |
| Trading activity | Buy/sell orders, completed round trips, holding durations and no-trade days |
| Risk | Sampled drawdown, concentration and rule violations |
| Execution quality | Rejections, partial fills, timeouts and execution prices |
| Decision quality | Verified versus unsupported claims, stale evidence and reasons for skipped trades |
| Comparison | Cash and a preselected hypothetical buy-and-hold benchmark |

Calculate win rate from **completed buy–sell round trips**, not from individual orders. Do not count an unsold profitable holding as a completed winning trade.

Maintain two separate results:

```text
Broker-account P&L
    = ending equity - starting equity - deposits + withdrawals

Project P&L
    = broker-account P&L - operating costs paid outside the account
```

Do not subtract brokerage fees twice if they already reduced the account’s cash.

For example, a €2 brokerage gain with €3 of externally paid API costs means the project lost €1.

The LLM’s review should answer: What happened? Which decisions had adequate evidence? Which controls worked or failed? What hypothesis deserves further testing?

A profitable week does not, by itself, justify changing the strategy or increasing capital.

## 10. Operating costs and taxes

### Keep API expenditure separate from the €50

X currently lists post reads at **$0.005 per returned post**, with other resource types priced separately. [X Developer Platform](https://docs.x.com/x-api/getting-started/pricing)

For an illustrative 22-session month:

| Collection limit | Posts returned | Post-read cost |
|---|---:|---:|
| 10 posts × 2 runs per session | 440 | **$2.20** |
| 25 posts × 2 runs per session | 1,100 | **$5.50** |
| 100 posts × 2 runs per session | 4,400 | **$22.00** |

These calculations exclude other billable resources, taxes and additional requests. Limiting collection also limits coverage; the report should say when relevant news may have been missed.

Start with a small, explicitly approved operating budget. Log actual LLM token usage and costs, cap X pagination, and stop paid analysis when its budget is exhausted. Existing-position monitoring should not depend on another paid LLM response.

**If €50 is your entire project budget, including APIs, you must allocate part of it to operations and reduce the trading deposit accordingly.** The design cannot both invest the full €50 and treat ongoing services as free.

Trading 212 currently lists commission-free Invest trading and a 0.15% FX fee where conversion applies, plus applicable third-party charges. Thus a €45 foreign-currency purchase and similar-sized sale imply roughly €0.135 in FX fees alone, before other costs. [Trading 212](https://helpcentre.trading212.com/hc/de-de/articles/11471996799517-Welche-Geb%C3%BChren-fallen-bei-Invest-ISAs-und-SIPP-an?utm_source=chatgpt.com)

### Tax records

For German tax residents registered under Trading 212 EU, the broker states that automatic taxation covers relevant Invest transactions from **5 January 2026**. Confirm your actual account entity and tax status. [Trading 212](https://helpcentre.trading212.com/hc/en-us/articles/24308101760029-How-am-I-taxed?utm_source=chatgpt.com)

The bot should retain broker statements, actual withholding entries, dividends, fees, execution prices and currency conversions. It should **reconcile to the broker’s tax documents**, not invent its own definitive tax liability from the LLM’s estimates.

## 11. Implementation and launch plan

| Phase | Deliverable | Exit condition |
|---|---|---|
| **1. Connectivity and permissions** | Broker demo, X collector, price feed and LLM adapter | Access, costs and permitted data processing verified |
| **2. Read-only operation** | Scheduled reports, knowledge retrieval and database | Runs complete reliably without order access |
| **3. Paper execution** | Full order lifecycle with a simulated €50 balance | Trading constraints and failure handling pass tests |
| **4. Shadow operation** | Decisions recorded against live data without real orders | No unexplained reconciliation or scheduling errors |
| **5. Restricted live pilot** | Explicitly enabled €50 cash experiment | You approve the configuration and residual risks |

Essential tests include simultaneous morning/midday jobs, restart after submission, a broker timeout followed by a successful fill, a partial fill, stale quotes, a market holiday, daylight-saving changes, a fabricated symbol, malicious text in a post, and an unexpected manual holding.

Paper trading should use the **same €50 limits**, rather than a large demo balance that conceals affordability problems.

### Initial configuration

```yaml
mode: paper

account:
  base_currency: EUR
  initial_capital_eur: 50.00
  automatic_topups: false
  borrowing_allowed: false

policy:
  max_distinct_stocks: 1
  max_order_submission_attempts_per_session: 1
  max_entry_total_eur: 45.00
  minimum_cash_after_entry_eur: 5.00
  allow_adding_to_position: false
  allow_short_selling: false
  allow_extended_hours: false
  emergency_exit_exception: false
  order_type: LIMIT

schedule:
  exchange_timezone: America/New_York
  report_timezone: Europe/Berlin
  premarket_minutes_before_open: 30
  execution_minutes_after_open: 15
  midday_exchange_time: "12:00"
  reconciliation_minutes_after_close: 10
  weekly_review_minutes_after_last_weekly_close: 30

news:
  provider: x_api
  max_posts_per_analysis: 10
  require_verified_material_claims_for_entry: true
  raw_content_to_external_llm: false  # Enable only after permissions review.

safety:
  unknown_order_status_blocks_trading: true
  stale_quote_blocks_trading: true
  invalid_llm_output_blocks_trading: true
  policy_changes_require_owner_approval: true
```

**The recommended first version is deliberately narrow: one account, a small watchlist, two scheduled analyses, at most one daily order, and a complete audit trail.** Its success criterion is initially reliable behaviour and honest measurement—not whether the LLM can produce a persuasive explanation for a trade.
